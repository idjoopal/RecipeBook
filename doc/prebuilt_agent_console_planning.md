# Prebuilt Agent Console — 기획 문서

> FastMCP + FastAPI 기반 Prebuilt Agent의 자체 프론트엔드 콘솔 기획.
> MCP·REST API로 연결 가능한 사전 구축형 에이전트들을 운영자와 사용자가 함께 다룰 수 있도록 설계.

---

## 1. 개요

### 1.1 프로젝트 배경

Prebuilt Agent는 LangGraph + MCP 기반으로 만들어지는 모듈형 에이전트 플랫폼이다. MCP와 REST API로 외부 클라이언트에 노출되도록 설계되어 있고, 원칙적으로는 어떤 플랫폼에도 연결될 수 있다.

하지만 MCP 엔드포인트만 노출하는 것으로는 충분하지 않다. 자체 프론트엔드 콘솔이 필요한 이유는 다음과 같다.

1. **MCP 클라이언트의 표현 한계** — Claude Desktop, Cursor 같은 일반 MCP 클라이언트는 텍스트·마크다운 중심이다. NL2Chart의 인터랙티브 차트, BI Agent의 대시보드, NL2SQL의 SQL + 결과 + 추론 흐름을 제대로 보여주지 못한다.
2. **연결 플랫폼 종속성 회피** — 고객이 사용할 채널이 제각각이라, 일관된 UX와 차별점을 보장할 자체 채널이 필요하다.
3. **시연·검증 경로** — 통합 전에 바로 동작을 보여주고 검증할 수 있어야 한다.
4. **운영 자산 관리의 거점** — MCP는 액션 채널일 뿐, 관리 UI가 아니다. 도메인 지식, 골든 SQL, PPT 템플릿 같은 자산을 편집·관리할 거점이 필요하다.

### 1.2 사용자와 사용 환경

- **배포 모델**: 1 배포 = 1 고객사. 멀티테넌시·LG CNS 운영팀용 별도 콘솔은 두지 않는다.
- **주 사용자**: 고객사 담당자.
- **역할 구분**:
  - **운영자(Admin)** — 콘솔로 직접 설정·관리하는 사람. 모델 키, 저장소, 에이전트별 자산을 다룬다.
  - **사용자(User)** — MCP·REST API로 에이전트를 호출해서 결과만 받아 쓰는 사람. 콘솔에서는 주로 가이드와 카탈로그를 본다.
- 콘솔 자체는 운영자가 더 자주 보지만, 가이드성 정보는 사용자도 볼 수 있어야 한다. 운영자/사용자 시점은 필요한 곳에서 토글로 분리한다.

### 1.3 핵심 가치 제안

- 단순 MCP 서버 묶음이 아닌, **"우리 환경에 맞춰진 에이전트 패키지"**로서의 사용성.
- 동작 시연부터 자산 큐레이션, 운영 관제까지 한 곳에서.
- 에이전트별로 다른 형태의 결과(SQL·차트·슬라이드·도구 호출 등)를 적절한 UI로 렌더링.

## 2. 정보 구조 (IA)

### 2.1 사이드바 (3개 영역)

```
Sidebar
├─ Overview                       ← 콘솔 랜딩 페이지
├─ Global admin
│   ├─ LLM API Key 관리
│   ├─ 공용 저장소 연결 상태
│   └─ 모델 헬스 체크
└─ Agents
    ├─ {Agent A} → 상세 (5탭)
    ├─ {Agent B} → 상세 (5탭)
    └─ ...
```

### 2.2 Agent 상세 — 5탭 구조

각 에이전트는 동일한 5탭 구조를 갖는다. Workspace 탭은 콘텐츠 관리가 필요한 일부 에이전트에만 노출된다.

```
{Agent} 상세
├─ Guide        — 에이전트 소개 + 사용/운영 가이드
├─ Test         — 샘플 입력 → 직접 호출 → 결과 확인
├─ Admin        — 리소스 연결, 모델, 엔드포인트
├─ Logs         — 호출 로그 + LangGraph 트레이스
└─ Workspace    — (조건부) 에이전트별 콘텐츠·지식 큐레이션
```

탭 순서의 의미: **학습(Guide) → 실험(Test) → 설정(Admin) → 모니터링(Logs) → 콘텐츠 큐레이션(Workspace)**. 운영자가 새 에이전트를 만났을 때의 자연스러운 흐름에 따른다.

## 3. 페이지별 상세

### 3.1 Overview

콘솔 진입 시 가장 먼저 보이는 랜딩 페이지. **"이게 뭐 하는 서비스인지 + 지금 잘 돌아가는지 + 다음에 뭘 할지"** 세 가지를 한 화면에 잡아준다.

#### 구성

| 영역 | 역할 |
|------|------|
| A. 헤더 | 콘솔명 · 한 줄 소개 · 테넌트명 |
| B. 시스템 상태 요약 | 메트릭 카드 4개 (등록 에이전트 수, 정상 동작 수, 모델 헬스, 저장소 상태) |
| C. Agents 카드 그리드 | 각 에이전트별 카드 (아이콘, 이름, 한 줄 설명, 상태 점, "자세히") |
| D. 시작하기 가이드 | 운영자 / 사용자 토글로 분기, 각 4단계 가이드 |
| G. 도움말 / 문서 링크 | 페이지 하단 (전체 문서, 트러블슈팅, 변경 이력, 문의) |

#### 운영자/사용자 토글 처리

페이지 상단(상태·카탈로그)은 두 시점 모두에게 가치 있는 공통 정보이므로 토글하지 않는다. **시작하기(D) 섹션에서만 토글**로 분기한다.

- 운영자 시점: ① LLM API Key 등록 → ② 공용 저장소 연결 → ③ 에이전트 활성화·리소스 연결 → ④ Test 탭에서 동작 확인.
- 사용자 시점: ① 사용할 에이전트 선택 → ② 엔드포인트 복사 → ③ 클라이언트에 등록 → ④ 호출 테스트.
- 각 단계에는 해당 메뉴로 점프하는 "이동 →" 링크가 붙는다.

#### 보류 영역

원래 E로 정의했던 **"MCP/API 연결 방법 가이드"**는 보류 상태다. 일반 클라이언트(Claude Desktop, Cursor, Python SDK 등)에 대한 가이드가 의미를 가지지 않는 환경(내부 플랫폼에만 연결되는 경우)이라 일단 제외했고, 내부 플랫폼 통합 방식이 확정된 후에 별도 섹션으로 추가하기로 한다.

### 3.2 Global Admin

플랫폼 전체에 공통 적용되는 인프라성 설정. 한 번 설정하면 모든 에이전트가 상속한다.

#### 3.2.1 LLM API Key 관리

- **등록된 Provider 목록 + 현재 상태** — Anthropic, OpenAI, Google, 자체 호스팅 OSS(EXAONE 등).
- **각 Provider별 API Key 등록·교체·회수** — 마스킹 표시, 만료일 노출.
- **연결 테스트** — 실제 호출로 가용성 확인.
- **기본 모델 설정** — 각 에이전트의 default가 될 모델. 에이전트에서 오버라이드 가능.

행 단위로 한 Provider가 한 줄을 차지하고, 한 줄에 아이콘·이름·마스킹 키·검증 시각·상태 배지·테스트/편집 액션이 모두 들어간다.

#### 3.2.2 공용 저장소 연결 상태

- **저장소별 연결 정보 + 상태** — OpenSearch (벡터 RAG·골든 SQL), 객체 저장소 (PPT 템플릿·업로드 파일), 메타 DB (에이전트 설정·로그).
- **각 저장소 연결 테스트** — 호스트·인덱스·컬렉션 단위로.

#### 3.2.3 모델 헬스 체크

- **모델별 현재 헬스 상태** — 정상·지연·이슈.
- **마지막 체크 시각 + 평균 응답 시간**.
- **자동 체크 주기 설정** — 기본 5분 등.
- **수동 헬스 체크 트리거** — "지금 다시 확인".

세 페이지 모두 행 단위 패턴을 공유한다. LLM API Key가 가장 풍부한 케이스고, 저장소·헬스는 같은 패턴의 변주다.

### 3.3 Agent 상세 — 탭별 구성

#### 3.3.1 Guide 탭

문서성 탭. **상단은 시점 공통, 하단은 운영자/사용자 토글**.

| 영역 | 위치 | 내용 |
|------|------|------|
| A. 에이전트 개요 | 공통 | 한 문단 설명 + 핵심 use case 2~3개 + 입출력 요약 |
| B. 기능과 한계 | 공통 | 가능 / 불가능 목록을 좌우 2열로 |
| C. 사용자 가이드 | 토글 (사용자) | 좋은 질문 패턴, 샘플, 알아두면 좋은 팁 |
| D. 운영 가이드 | 토글 (운영자) | 필요 리소스·사전 준비, 초기 설정, 흔한 운영 이슈 |

B의 일부는 MCP tool schema에서 자동 추출 가능하다(가능한 함수 시그니처 등). 사람이 손으로 쓰는 영역과 자동 영역이 섞이는 구조.

#### 3.3.2 Test 탭

운영자(혹은 사용자가 콘솔에서 직접 실행해보고 싶을 때)가 에이전트를 그 자리에서 호출해 동작을 확인하는 탭.

- **샘플 쿼리** — 칩 형태의 프리셋. 클릭하면 입력란에 자동 채워짐. 첫 사용자의 진입 장벽을 낮추는 핵심 장치.
- **질문 입력 + 실행** — 자유 입력 + 실행 버튼.
- **결과 표시** — **에이전트별로 형태가 다르다**. 이 부분이 자체 프론트엔드가 필요한 가장 강력한 근거다.
  - NL2SQL: 생성된 SQL + 검증 배지 + 실행 결과 테이블.
  - NL2Chart: 인터랙티브 plotly 차트.
  - PPT Creator: 생성된 슬라이드 미리보기 + 다운로드.
  - BI Agent: 인사이트 요약 + 근거 데이터.
  - Recipe Book: 호출된 도구 + 결과 요약.

#### 3.3.3 Admin 탭

운영자가 이 에이전트의 운영 정보를 다루는 곳.

- **리소스 연결 상태** — 이 에이전트가 의존하는 DB·OpenSearch·외부 API·도메인 자산. 각 항목에 상태 배지와 연결 테스트.
- **모델 설정** — Global Admin 기본값 상속 + 이 에이전트만의 오버라이드.
- **엔드포인트** — MCP / REST API URL + 복사. 사실상 이 에이전트의 "출구" 정보라 눈에 띄는 위치에.
- **활성화 토글** — 에이전트 ON/OFF.

#### 3.3.4 Logs 탭

- **호출 로그 리스트** — 시각·요청·상태·응답시간·토큰. 날짜·상태·검색 필터 지원.
- **트레이스 상세** — 한 행 클릭 시 인라인으로 펼쳐서 LangGraph 노드별 실행 흐름(disambiguate → plan → retrieve → generate → validate)과 각 단계 소요/토큰, 생성된 산출물(예: SQL), 결과 요약 표시.

별도 모달이 아닌 인라인 확장 패턴이라, 운영자가 여러 로그를 비교 가며 분석할 수 있다.

#### 3.3.5 Workspace 탭 (조건부)

콘텐츠 관리가 필요한 일부 에이전트(PPT Creator, NL2SQL, Recipe Book 등)에만 노출된다. 각 에이전트마다 다루는 자산의 성격이 다르므로 내부 구성도 다르다 (4장에서 상술).

##### "Workspace" 용어 선택 배경

호스트로 삼고 있는 플랫폼이 Builder / Hub / Router / Studio / Knowledge Lake 같은 모듈명을 이미 쓰고 있어서, 같은 단어를 피해야 했다. 후보:

| 후보 | 평가 |
|------|------|
| Studio | 호스트 플랫폼과 충돌 — 사용 불가 |
| Workbench | 손맛/공방 톤. NL2SQL 같은 기술 에이전트엔 살짝 어색 |
| Library | "보관소" 뉘앙스가 강해 생성 작업에 안 어울림 |
| Workspace | 표준 UI 어휘, 생성/편집/관리를 폭넓게 포괄, 충돌 없음 |

**Workspace로 최종 결정**. 디지털 네이티브 환경에서 표준 어휘이고, 만들기·편집·관리 모두 자연스럽게 담는다.

## 4. 에이전트별 Workspace 상세

> 본 문서 작성 시점에 PPT Creator / NL2SQL / Recipe Book 세 에이전트의 Workspace 구성을 시안 수준에서 정리했다. 세부 디자인은 후속 단계에서 다룬다.

### 4.1 PPT Creator

운영자가 회사 표준 PPT 템플릿을 등록·정제·테스트하는 곳.

#### 3-뷰 흐름

1. **템플릿 갤러리 (메인 뷰)** — 등록된 템플릿 그리드. 썸네일 + 이름 + 최근 수정일. "새 템플릿" / "PPT 업로드" 액션.
2. **템플릿 등록·편집 (디테일 뷰)** — 업로드 시 자동 추출된 placeholder를 사람이 정제. 슬라이드 썸네일 리스트 + 선택 슬라이드 미리보기. placeholder 정의 (이름, 타입, LLM 채움 지침), 메타데이터.
3. **미리보기·테스트 (모달)** — 샘플 입력으로 채워진 PPT 미리보기 + 다운로드.

#### 가치 포인트

- PPT 파일을 그대로 올리면 자동 추출되는 흐름이 운영자 진입 비용을 크게 낮춘다.
- Placeholder 정의가 이 Workspace의 진짜 핵심 작업. 자동 추출이 완벽하지 않을 때 운영자가 손으로 다듬는다.

### 4.2 NL2SQL

운영자가 에이전트의 도메인 지식과 골든 SQL 패턴을 큐레이션하는 곳.

#### Sub-tabs

1. **용어 사전 (Glossary)** — 용어, 정의, 별칭. 행 단위로 표시. 회사 산식 참조 가능.
2. **회사 산식 (Formulas)** — 비즈니스 계산식 정의. SQL 표현과 함께.
3. **Golden SQL** — 검증된 SQL 패턴. 자연어 질문 → SQL 매핑 저장.

#### 가치 포인트

- **재임베딩 트리거**가 사전 상단에 있음. 운영자가 용어를 고치고 바로 반영하는 흐름이 끊기지 않게.
- 마지막 임베딩 시각 노출 — "지금 변경 사항이 반영된 상태인가" 즉시 판단 가능.

### 4.3 Recipe Book

운영자가 에이전트에 사용할 skills.md를 등록·관리하고, 도구 description을 다루는 곳.

#### Sub-tabs

1. **Skills** — 등록된 skills.md 파일들. 각 항목에 아이콘, 이름, slug (mono font 식별자), 한 줄 설명, 마지막 수정일. 새 skill 등록 / 업로드.
2. **도구 Description** — 이 에이전트가 노출하는 MCP 도구별 description 편집.

#### 가치 포인트

- skills.md는 파일 단위 자산이므로 **업로드** 진입 흐름이 강조됨.
- skill의 slug (예: `meeting-summary`)를 항상 함께 표시 — 도구 description이나 운영 로그에서 참조될 식별자다.

## 5. 주요 디자인 결정 요약

### 5.1 시점 분리는 토글로, 공통 정보는 노출

운영자/사용자 두 시점을 모두 다뤄야 하지만, 두 페이지를 따로 두지 않는다. 공통 정보는 그냥 노출하고, 시점에 따라 다른 부분만 토글로 분기한다. 적용 위치:

- Overview의 시작하기 섹션
- Agent Guide 탭의 사용자/운영 가이드 영역

다른 영역(상태 대시보드, 카탈로그, Admin·Logs 등)은 토글 없이 단일 뷰.

### 5.2 "핵심만 우선" 원칙

모든 페이지 설계에서 "핵심 항목 + 선택 항목"을 명확히 구분했고, **현재 단계에서는 핵심만 포함**하는 것으로 결정했다. 선택 항목은 운영 데이터가 쌓이거나 사용자 피드백이 들어오는 시점에 단계적으로 추가한다.

선택 항목에 포함시켰지만 현재는 보류된 것들:

- 사용량·비용 메트릭
- 사용자/역할 관리
- 에이전트별 Tool/Function 목록 노출
- Eval / Quality metrics
- 변경 이력 / 관련 링크 (Guide 탭 하단)
- 알림 / 모니터링 설정

### 5.3 탭 순서의 의미

`Guide → Test → Admin → Logs → Workspace`

운영자가 새 에이전트를 마주했을 때의 자연 흐름: **알기 → 써보기 → 설정 → 관제 → 콘텐츠 큐레이션**. 첫 진입자에겐 Guide가, 매일 사용자에겐 Test·Admin·Logs가 진입점이 된다.

### 5.4 자체 프론트엔드의 핵심 차별점

설계의 모든 결정은 결국 다음 한 줄로 수렴한다:

> 같은 Test 탭이라도, 에이전트마다 결과 영역의 표현이 다르다 — NL2SQL은 SQL + 테이블, NL2Chart는 plotly, PPT Creator는 슬라이드 미리보기, BI Agent는 인사이트 요약.

이게 일반 MCP 클라이언트로는 불가능한, 자체 프론트엔드의 가장 강한 명분이다.

## 6. 향후 결정 사항

### 6.1 보류 영역

- **Overview의 MCP/API 연결 가이드 (구 E)** — 호스트 플랫폼 통합 방식 확정 후 별도 섹션 또는 Help 페이지로 추가.
- **에이전트별 Workspace 세부 디자인** — PPT Creator의 슬라이드 편집기, NL2SQL의 골든 SQL 편집 UI, Recipe Book의 skills.md 에디터 등은 시안 수준만 정의됨. 후속 단계에서 상세화.

### 6.2 Phase 2 확장 후보

- 사용량·비용 추적 (LLM 티어별, 에이전트별)
- 사용자/역할 관리 (단일 테넌트 내 다중 사용자)
- Eval / 회귀 테스트 운영 (Workspace에 변경 가했을 때 영향도 측정)
- 알림 설정 (헬스 이슈, 에러율 임계치)
- 변경 이력 / 감사 로그

### 6.3 결정 필요

- Workspace 보유 에이전트가 늘어났을 때 sub-tab 구조의 확장 한계
- 사내 표준 디자인 시스템과의 정합성 검토 (있다면)
- 모바일 / 작은 화면 대응 범위
